# الأمان — النسخة المبسّطة

موقع بدون حسابات زبائن يعني سطح هجوم أصغر بكثير من الأصل. هذه هي طبقات الحماية الفعلية المطبّقة:

| الحماية | أين | ملاحظة |
|---|---|---|
| HTTPS/SSL | الاستضافة (Vercel تفرضه تلقائيًا) | إجباري، بدون استثناءات |
| حماية من Clickjacking وحقن خارجي | `next.config.js` (رؤوس CSP, X-Frame-Options) | على كل صفحات الموقع |
| حماية الجلسات | Supabase Auth (كوكيز HttpOnly + Secure) | لا تخزين في localStorage إطلاقًا |
| عزل لوحة الإدارة | `middleware.ts` (تحقق من الجلسة) + RLS في قاعدة البيانات (طبقة مستقلة) | حتى لو تجاوز أحدهم الواجهة، RLS ترفض في قاعدة البيانات نفسها |
| منع أي زائر من قراءة رسائل غيره | سياسة RLS على جدول `inquiries`: INSERT فقط للعموم، SELECT للأدمن فقط | مُختبرة عبر `supabase/schema.sql` |
| SQL Injection | Supabase client يستخدم استعلامات مُعامَلة (parameterized) دائمًا | لا بناء استعلامات بدمج نصوص في أي مكان بالكود |
| حماية المفاتيح الحسّاسة | فقط `anon key` العام في كود الواجهة؛ لا مفاتيح سرية على الإطلاق في هذه النسخة | لا يوجد مزوّد بريد أو دفع مربوط حاليًا |

## ما الذي أُسقط عمدًا (ولماذا هذا آمن)

- **لا تحقق بريد إلكتروني / لا reCAPTCHA**: بما أن الزائر لا يملك أي صلاحية غير الإرسال (INSERT)، ولا يستطيع القراءة أو التعديل، فحتى رسائل مزعجة (سبام) أقصى ضررها إزعاج بسيط في لوحة الإدارة — يمكن حذفها بضغطة، وليست ثغرة أمنية حقيقية. إن أصبح السبام مصدر إزعاج فعلي لاحقًا، إضافة reCAPTCHA تتم بسطرين فقط في `submitInquiry` دون أي تغيير هيكلي.
- **لا نظام أدوار متعددة**: يوجد دور واحد فقط (أدمن)، محدّد صراحة في جدول `admins` — أبسط من نظام صلاحيات متعدد وأصعب في الاستغلال الخاطئ.

## لإضافة أدمن ثانٍ لاحقًا

```sql
insert into admins (user_id) values ('UUID-حساب-الأدمن-الجديد');
```
لا حاجة لأي تعديل في الكود.
